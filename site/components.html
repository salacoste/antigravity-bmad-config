What the template adds

A thin layer over pinned upstream BMad: one orchestrator skill, two rules, twenty-nine skills it routes across, and a version pin that decides when any of it changes.

Three layers, one of them yours

Everything below the middle band is installed by ./setup.sh from the pinned version — the BMad runtime and all 29 skills — and belongs to the installer, never to you. The middle band is what this repo commits: the orchestrator plugin, its two rules, and the presets. The artifacts everyone produces land in _bmad-output/, your project's working data.

The orchestrator: /bmad-orchestrate

One skill is the front door for every BMad session. /bmad-orchestrate works out where your project is, then routes you to the right skill — it never does a persona's job itself.

What it does

  • Single entry point that routes work across the BMad skills this template installs.
  • Detects which planning artifacts already exist and classifies your state — an empty project gets the Day One path; from there it's brief → PRD → architecture → spec/stories → sprint → build → review.
  • Sequences Clarify → Plan → Build → Learn with explicit handoffs: a short Handoff receipt after each phase records what was completed, what's next, and any open questions.
  • Multi-option decisions go through the ask_question tool with concrete options — no free-text guessing.
  • Never edits _bmad/ except _bmad/custom/.

Ground rules

The two rules

bmad-workflow.md Always on: routes BMad work to the installed bmad-* skills; never edits _bmad/ outside _bmad/custom/.

The rest of _bmad/ is installer-managed — regenerated by ./setup.sh from the pinned version. Multi-option decisions during BMad work go through ask_question, artifacts stay under _bmad-output/, and when no skill obviously fits, bmad-help does.

bmad-artifacts.md Planning artifacts under _bmad-output/ are changed through their owning skill; never deleted to "clean up."

Route changes through the skill that owns the document; for mid-implementation course changes use bmad-correct-course. Story files keep their status current while you implement — review, retrospective, and sprint planning all read that state.

It's all plain files — browse the plugin: .agents/plugins/antigravity-bmad/

The pin: .bmad-version

The exact BMad version — 6.12.4 — is recorded in .bmad-version, the single source of truth. setup.sh, the Makefile, and CI all read it, so a BMad release can't change your project under you.

How updates happen

Updates are deliberate — three make targets, run on demand:

Changing the pin

  1. Edit .bmad-version to the version you want.
  2. Run make smoke-test.
  3. Fix any breakage it reports.

CI runs the same checks on every push — and weekly, to catch an upstream delisting even when nothing changed on your side.

BMad v7 is alpha and not npm-pinnable — the template stays on v6 until v7 is stable, and avoids the v6 shim skill names v7 removed, like bmad-create-story.
